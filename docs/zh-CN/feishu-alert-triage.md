# 飞书群告警自动排查

CodeBridge 使用 `@larksuiteoapi/node-sdk`，不依赖飞书 CLI。告警监控以所配置机器人的应用身份定时调用群历史消息接口，处理指定机器人的新消息，复用已有 Agent Session 和飞书流式卡片回复。普通群消息自动回复和主动采集机器人告警是两个入口。

## 配置

当前已有按群配置的采集、审批与状态投递能力；本地候选已在“任务”中提供告警配置与规则维护，尚未发布或切换实例，见[交付状态](../release-status.md)和[渠道自动化规划](channel-automation-roadmap.md)。

本地候选优先使用“任务 → 新增告警”：选择渠道与群名，成员自动加载后按姓名勾选负责人；唯一群和唯一机器人来源自动选中，任务名自动生成。新任务默认停用，确认设置后再启用。群名来自机器人所在群列表，成员姓名来自本应用的群成员列表；同名成员附身份尾号，不跨应用或渠道推断身份。

来源以近期机器人消息供辨认，群成员接口本身不列出机器人。来源不唯一时需要选择；没有近期消息时可刷新或在高级设置指定已核实的来源。名称覆盖、审批人、Skill 路径和手工 ID 都在高级设置，负责人不会自动变成审批人。原案件、游标、规则和已有身份继续使用。

以下 YAML 为手工配置参考，不是日常页面的必填项：

在配置中现有的 `feishu` 节点下合并以下 `alertMonitor`，不要新增第二个同名节点。填写真实群、发送方应用 ID，以及审批人在当前机器人应用下的 Open ID：

```yaml
feishu:
  # 保留已有 appId、appSecret 和 policy
  alertMonitor:
    enabled: false # 初次配置保持停用，在专用测试群验收后再明确启用
    pollIntervalMs: 60000
    lookbackMs: 600000
    dedupWindowMs: 1800000
    maxConcurrent: 2
    incidentRetentionMs: 604800000 # 终态案件 7 天后从状态文件移除，话题恢复普通行为
    statusReactions:
      investigating: OnIt
      waiting: OneSecond
      resolved: DONE
      no_action: CrossMark
      blocked: Sigh
    groups:
      - chatId: oc_your_alert_group
        senderAppIds:
          - cli_your_alarm_sender
        approverOpenIds: # 可多人；旧配置的 ownerOpenId 仍可用，等价于单个审批人
          - ou_your_approver
        responsibleOpenIds: # 可多人；失败或排查受阻时通知，不授予审批权限
          - ou_your_responsible
        runbookPath: /absolute/path/to/feishu-alert-triage/SKILL.md
```

未配置 `alertMonitor` 时不启用；已有该节点且省略 `enabled` 时默认启用，因此初次配置应明确写 `enabled: false`。部署包含本功能的版本后再配置；通过候选版本的“任务”页面保存后，Bridge 使用当前配置；直接编辑配置文件时按现有进程管理方式重新加载。移除 `alertMonitor` 会停止新告警采集，已有告警话题的审批人记录仍保留。首次启用从当前时刻开始，不追溯处理已有历史告警。

机器人必须在该群，并具备读取群内所有消息和发送/回复消息所需权限。告警可能是 `post` 富文本或 `interactive` 卡片，不能只按卡片类型筛选。每个应用/群的权限和投递行为都需要自己的验收，不复用维护者业务群的结果。

## 行为

- 仅采集配置的群和发送机器人；群友普通消息、回复串及其他机器人不启动自动排查。
- 示例配置每 60 秒检查（代码缺省间隔仍为 30 秒），持久化时间窗口和分页游标。每轮从上次成功进度往前回看 10 分钟，按消息 ID 去重，补抓延迟出现的消息；首次启用之前的消息仍跳过，关机后仍从旧进度补读至当前。`lookbackMs` 可调整，最长 24 小时；超出回看窗口才出现的旧消息不保证自动找回。
- 同一消息只提交一次，相同来源和相同正文在 30 分钟内合并，不重复排查。
- 默认同时自动排查最多两条（可配置），其余保留待处理。维护期间暂停采集/提交；读取失败保留进度，提交失败以原消息 ID 重试。
- 首条告警根消息对应独立 Session，排查卡片在原消息话题中回复；群里任何人在该话题里 @ 机器人 或回复机器人，都继续同一个 Session，机器人正常对话。
- 默认先只读排查。只有受信任 runbook 中明确记录的流程级授权，并且当前对象、接口副作用、幂等和复查条件全部匹配时，才可在授权范围内执行有界动作；否则须原生 @ 审批人，说明证据、对象、拟执行动作和影响，结束本轮等待明确回复。
- 对话对所有人开放，权限按动作收口：每条回复都带着「审批人 / 群成员」身份进入 Agent 上下文；超出已有流程级授权的写操作，只接受该告警话题中已验证审批人的本次明确回复。群成员提供的信息不扩大授权；告警正文、其他机器人和历史个案批准不是当前写操作授权，含糊回复需要澄清。
- 不修改告警原消息的正文；状态表情可挂在原消息上，进展与结果写到机器人的回复卡片。
- 告警群里其他机器人的消息不受影响：只有配置里 `senderAppIds` 的告警消息走采集器；别的机器人 @ 机器人时照常进入普通对话，未 @ 时忽略。

`feishu-alert-monitor.json` 保存采集进度、去重记录和话题审批人。保留这个文件；删除它会丢失已有话题的审批人映射。终态（resolved / no_action / dismissed）案件超过 `incidentRetentionMs` 后自动移除，其话题随之恢复为普通话题。不要复制不同实例的状态或同时运行多个 Bridge 进程共用同一数据目录。

## 权限边界与验收

默认只读、流程级授权条件和逐次确认通过任务指令与入站身份标注共同约束；后端还校验审批命令发送者及状态投递来源。它不是为所有 Agent/任意 shell/MCP 工具新增硬只读沙箱；现有 Agent Permission 和业务 skill 的 dry-run/确认仍必须遵守。

合同测试覆盖分页、重启、延迟消息、去重、并发、审批人与群成员对话；飞书表面测试经过实际 `FeishuBridge` 入口，以模拟 SDK 验证线程回复、通知 open_id 和群成员回话路由。真实 SDK 群消息读取成功不等于真实群内整个自动流程已验收。发布后需用一条新告警验证原话题排查、原生 @、群成员回复及终态。


## 原卡片表情与标准流程

状态表情直接挂在原告警消息上，不发送单独表情消息。等待确认（waiting）时，后端原生 @ 当前群配置的审批人；失败、中断或排查受阻（blocked）时，原生 @ 当前配置的告警负责人。负责人不自动获得审批权限，摘要是具体待办；Agent 不再额外重复发送 mention。旧配置未设置 responsibleOpenIds 时继续通知审批人；在“任务 → 告警”选择负责人并保存后独立配置，不需要改写旧案件。负责人调整后，既有待处理案件按当前配置通知，发送失败保留重试。

Agent 使用 `fcb alert status <investigating|waiting|resolved|no_action|blocked> "证据或待办"`。`/outbound/alert-status` 仅接受当前活动 Run 的持久化飞书来源，不接受调用方自选群/消息，也不向外部 publisher 凭据开放。状态记录与 Reaction 投递分离保存，失败后重试；只替换本应用自己的五种状态表情，保留其他人及本应用非状态表情。

`resolved` 要有业务复查证据，`no_action` 表示核实不需操作。Agent Run 已结束但未提交可核验结论时改为 `blocked`，不会自动标成功。重复告警的原卡片投影到同一案件状态。

配置 `runbookPath` 后，每次新告警及后续回复重新读取该 SKILL。`/approve`、`/deny` 这类审批命令只认审批人，群成员发出时会在话题里得到提示而不会生效。SKILL 再读取当前告警矩阵，复用业务 skill 的只读查询与确认规则；未知类型添加 draft，真实证据或用户纠正更新已有分支。缺失/不可读的流程文件不能静默绕过。

试运行使用专用测试群的新消息验收，不手写或复制案件状态文件。已有实例升级应保留原状态文件、游标、审批人和 Skill 路径。


## 快速分类与人工结案

优先 SKILL、矩阵与同群同类型的历史记录；已明确的通知类按规则直接归类，只有需要本单状态时才补最小查询。矩阵没有覆盖的新类型须先核对当前对象状态，再按需检查来源代码、日志和链路；排查受阻时 @ 负责人，确需业务决定时 @ 审批人，不能把可自行完成的只读排查交回用户。

系统依据规则判定无需操作仍为 `no_action` / CrossMark。群里任何人在关联话题明确回复“无需处理”“不用处理”“不需要处理”等，后端记录真实发送人后写入 `dismissed` / DONE，停止本案排查；这表示人工结案，不表示修复成功。结案不需要审批人身份。Agent 状态命令不能伪造结案，迟到结果也不能覆盖。任何人明确“重新排查”可重新开启。每次结案（回复或 DONE）机器人在该告警话题回一句回执，写明结案人（按群成员列表取显示名，取不到时写“审批人”/“群成员”）和方式，并注明不代表故障已修复；已结案再次结案不重复回执，重开后再结案会再回一次。回执发送失败只记日志，不影响结案和 DONE 表情。

排队也先标 OnIt；正文不可读的每张卡单独进入 waiting 并请求补充，不能因缺内容或去重而不登记状态。投递失败仍有持久待投递记录，不能声称接口失败时表情已经可见。

重复卡按同一来源、业务对象及问题归并；仅展示用的独立告警时间/次数、trace/request 行不作为区分依据，保留单号、SKU、仓库、数量及错误条件。未结案件保持关联，结案后同案重复卡继承 DONE；不同业务对象不因标题相同而合并。任何群成员在任一关联原卡片、或该告警话题里任何一条消息（包括机器人自己的回复）上点击飞书 DONE 即结案，后端通过消息的话题根定位案件，同案重复卡同步 DONE；不再另外询问原因。机器人自己的 DONE 和删除表情均不触发结案/重开。其他表情不触发任何动作，但会按案件汇总（表情 → 点了的人，同案重复卡合并、删除即扣减），在机器人下一轮回复时作为参考上下文注入，明确标注不是指令也不是授权；飞书每个人每次点击都是一条独立事件，SDK 只去重不聚合，汇总由后端完成，因此再多表情也不会起任务。这些汇总只来自实时事件，定时回查仍只补 DONE。SDK reaction 事件及时处理，定时只读回查每群每轮最多 20 张已登记卡片，持久化轮转进度补偿断线；积压时完成回查可能超过一分钟。明确重新排查后，不将旧 DONE 当作再次结案。

普通告警逐个确认原因，不同订单/任务不能只按标题批量关闭。纯通知只有匹配 SKILL 同目录 `references/notification-rules.json` 内唯一已核实规则才一起结束：规则需 verified=true、kind=notification、明确来源、完整标题、逐行原因条件和证据。每张原卡片分别标记 CrossMark；有人再点 DONE 则记录人工结案。缺规则、草稿或匹配歧义均回退逐条判断；未核实的规则应保持草稿/停用，不因名称相似自动归类。

## 原话题定向提醒

### 当前审批人明确要求人工结案

状态工具支持 `status="dismissed"`，CLI等价为 `fcb alert status dismissed "按本次明确指令人工结案；非业务恢复"`。后端固定当前活动Run、原群/话题及来源消息，从飞书重新读取真实用户正文，核对当前审批人及明确结案指令，并拒绝否定、疑问、引用材料和机器人来源。不能通过伪造summary、发送人或订单ID取得权限。仅接受本案件当前已登记且未被新回复取代的指令；群配置撤销或Run结束后拒绝迟到请求。

成功时记录 `dismissed` 并给关联原卡添加DONE，不取消正在生成回复的当前Run，也不再单独发一条结案回执。DONE只表示人工决定停止跟进，不证明业务恢复。若关闭已记录但表情投影未确认，工具返回明确错误，重试只同步现有状态，不重放业务或重写较新的决定。`resolved`和`no_action`不替代人工DONE。

该动作不直接授予跨订单、后续同类型的自动结案权限，也不修改SKILL；后续规则须按现有可信授权流程持久化，不能以新增工具绕过此前被拒绝的规则写入。

### 逐单排查反馈后的持续授权结案

群审批人已经明确确认后续同类处理口径时，由 SKILL 维护者同步该群矩阵、流程以及同目录 `references/closure-rules.json`。这份机器规则与纯通知规则分开：纯通知可以免查并批量归类；`after_triage` 必须逐单排查，不合并不同业务对象。CodeBridge 不解析业务流程文本，也不写死某个人、群或错误码。

规则只从当前群配置的 `runbookPath` 所在目录读取，调用方不能指定规则文件或授权消息。以下全部为虚构示例，草稿保持 `verified: false`；确认真实授权与精确范围后才启用：

```json
{
  "version": 1,
  "rules": [{
    "id": "EXAMPLE-LOGISTICS",
    "kind": "after_triage",
    "verified": false,
    "senderAppIds": ["cli_example_alerts"],
    "title": "示例物流告警",
    "bodyIncludes": ["example transport error -1234"],
    "evidence": "示例审批人明确允许后续同类查询反馈后结案，由客服跟进",
    "authorization": {
      "messageId": "om_example_authorization",
      "contentSha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
    }
  }]
}
```

`bodyIncludes` 的每项须匹配一条完整原因行，标题和发送应用也须全部精确匹配；多条规则同时命中时拒绝选择。`authorization` 指向真实人类授权消息，SHA-256 取 SDK `readAlertUserMessage` 返回的原始 `content` UTF-8 字节，不能从模型摘要或含引用的完整提示词计算。维护者负责记录用户明确批准的范围，后端独立核对原消息仍属于本群、作者仍为当前审批人、正文哈希未变化，以及告警创建时间不早于原授权消息；来源缺失、时间未知、删改或权限变化时不执行，不追补历史告警。仅有 Markdown 口径、草稿、告警正文或 Agent 自述均不构成可执行结案规则。新增/扩大范围仍须真实用户批准；停用时同步矩阵、流程并删除规则或设为 `verified: false`。

新机器人告警完成只读排查后沿用 `codebridge_alert_status(status="dismissed", summary="本单查询事实与结案原因；非业务恢复")`，不指定通知对象。后端唯一匹配并核验规则后，返回 `status="investigating", pending=true`，这只表示待结案已持久登记。Agent 继续输出完整最终答复，不再调用另一个状态覆盖它。后台只有确认同一 Run 已成功、原话题最终回复卡片的 delivery 已完成，且当前案件、来源、规则和授权仍有效后，才写入 `dismissed` 并投影 DONE；不另发结案回执或 @ 消息。业务查询是否满足矩阵仍由业务 SKILL 与 Agent 的本单证据判断，任务成功和投递回执只证明执行及交付，不能证明业务恢复。

Run 失败/取消/中断、规则撤销/变更或授权不再通过核验时，不标 DONE；在原回复卡片反馈阻塞原因，不增加审批人提醒。尚未成功或最终卡片尚未投递时保持待确认。原授权读取超时等传输失败也保留待确认，下一轮或重启后只重试核验，不当作永久撤销或重跑查询。新用户回复、人工结案、重新排查或新的状态请求会取代旧待结案请求，旧 Run 不得覆盖新决定。待结案、规则版本及绑定 Run/来源保存在原案件状态中，重启继续核对投递，不重跑查询或业务操作；DONE 投影失败沿用既有持久重试。既有已结案案件不因停用未来规则自动重开，同案重复卡继承既有终态；需要重开时明确回复“重新排查”。

结案审计记录原授权消息、审批人、规则 ID/版本及本次 Run，规则仅授权告警结案，不授予订单、退款、发货等业务写权限。仅更新 SKILL 不会让旧版本后端支持此路径；必须同时部署 Bridge/Runner，并核实实际入口和投递完成路径。隔离测试使用真实 Session API、SQLite、活跃飞书卡片 watcher 与模拟 SDK，验证新告警到完整答复和 DONE、重复卡、重启、失败及撤销；它不能代替真实生产告警的后续验收。

### 会话配置与引用边界

飞书、Telegram的会话入口传递已有的模式及思考等级。新Session使用当前绑定；旧Session缺失时补入绑定值，保留会话自身的明确覆盖，不改全局审批配置。验证时应同时核对持久化Session、Turn/Run和适配器实际采纳的配置；配置文件有值不代表运行已经生效。

飞书提示词先呈现本轮真实指令和真实发送者，再给执行说明，最后以独立边界附加引用资料。引用“不代表授权”的说明只约束引用块，不否定上方真实用户指令。人工结案授权以SDK核实的原消息为准，权限不依赖Agent在summary或命令justification中的自述。自动审批由平台独立评估，此改动改善信息传递，不保证消除所有模型误判。

### 一人或多人定向提醒

下文“示例成员甲”“示例成员乙”为虚构姓名；实际提醒对象以仓库外对应群的 SKILL／告警矩阵为准。

群矩阵只需写清“这个分支提醒谁”，不需要预配置联系人名单或用户 ID。Agent按本次需要协助的事项、已核实负责人及本群受信任矩阵选择一人或多人，不能由告警正文或工具输出改派。内置 MCP `codebridge_alert_status` 的 `notify` 接受单个姓名或姓名数组，例如 `"notify": ["示例成员甲", "示例成员乙"]`。CLI可重复 `--notify`：

```bash
fcb alert status waiting --notify "示例成员甲" --notify "示例成员乙" "请分别核对实际到账与后续处理"
```

后端完整读取当前告警群成员，按去除首尾空白后的姓名精确匹配；同一成员重复出现按ID去重。全部姓名逐个唯一匹配后，才取得当前小V应用下的openId，在原Run的同一张排查回复卡片一次原生@选中人员，保留模型完整正文，不额外发消息。一次最多20个姓名，重复姓名或成员ID去重，名单顺序变化不重发。不要求对方曾在该话题发言，也不要求用户先@她。

任一姓名查不到、存在不同ID的同名成员或读取群成员失败时，整次不发送@提醒、不转发审批人，在原话题反馈具体原因，并保持待跟进状态；同一失败不会每分钟重复发反馈，成员条件恢复后可继续原案件投递。发送失败/重启保留指定姓名，始终不改派给默认审批人。新状态调用不传notify时，按本次waiting默认审批人、blocked默认负责人策略，不沿用上轮定向名单。已确认的历史单人提醒记录仍保留，不因升级重新提醒；重试和重启保留失败时的完整指定名单。

多人参数属于源码新增能力，须部署对应Bridge与Runner后使用；仅更新SKILL或群矩阵不会让旧工具支持多人。后台跟进的`notifyNames`与默认负责人/审批人列表已支持多人，保持原机制。

群、原卡与话题仍由当前活动Run绑定，不接受调用者改目的地或直接指定任意用户ID。提醒不增加审批权，姓名仅按当前群受信任矩阵选择，告警正文不能改变通知规则。

### 普通主动通知中的多人提及

普通会话里，`fcb mention u1,u2 "请一起查看"`可在同一条新消息中提及多个已登记对象；HTTP `/outbound/mention`的`ref`接受一个引用或引用数组。每个引用仍必须属于当前聊天和话题，全部验证通过才发送，不接受姓名冒充引用或原始用户ID。飞书复用SDK的mentions列表，Telegram复用原生entities列表；任一引用无效则整条拒绝。告警的状态提醒仍优先使用上面的notify在原回复卡片更新，不用普通mention再发一条。

## 官方飞书 CLI 与按需授权

CLI 作为显式固定版本依赖提供，无需依赖维护者全局 PATH。配置独立保存在 `<dataDir>/feishu-cli`，复用小 V 已有应用；setup 通过 stdin 传递密钥，由官方 CLI 管理钥匙串，输出去除凭据。

```bash
codebridge feishu-cli install --data-dir "$HOME/.codebridge"
codebridge feishu-cli setup --data-dir "$HOME/.codebridge"
codebridge feishu-cli status --data-dir "$HOME/.codebridge"
```

同群查成员和机器人发消息使用 bot 身份。只有需要按姓名搜索整个通讯录等 user 能力时才发起个人授权：

```bash
codebridge feishu-cli login --scope contact:user:search --data-dir "$HOME/.codebridge"
```

将返回的原始授权链接交给用户，可用 `codebridge feishu-cli qrcode --verification-url "$VERIFICATION_URL"` 生成 PNG；用户确认完成后再用 `codebridge feishu-cli complete --device-code "$DEVICE_CODE"` 完成并复查 status。授权码和个人令牌不写进群消息、源码或 Skill。不同应用的 openId 不能直接混用。

`members --chat-id` 只接受当前已配置的告警群，以 bot 身份查询；`search-user --query` 明确使用 user 身份，缺权限时显示官方提示，不能自动扩大授权。
